## 1. Decision and scope

Select suffix-free `0.8.0` for the additive public-package boundary after
published `0.7.1`. The release publishes the accepted Core and Node subpaths,
read-only historical DAG CLI, historical result and schema, and declaration-
identity correction while retaining Grammar 6 and CLI Contract 7.

The exact public source boundary is 45 commands, 21 root schemas, 122 root and
Node runtime exports with reference identity, and 45 portable Core runtime
exports. The added command is `dag history`; the added result is
`Perttool.HistoricalGraphResult.v1`. Existing commands, result meanings,
governance, plan assurance, temporal start authority, history safety, and
source-preserving write behavior remain compatible.

Private workspace packages under `adapters/lsp`, `adapters/vscode`, and
`adapters/mcp` remain excluded from the public npm tarball. This release does
not publish a VSIX, create public adapter package identities, add editor or MCP
mutation, implement `SCM-001`, move npm `latest`, advance a plan, or mutate an
Issue.

## 2. Work packages and authority

The dependency order is fixed by `plans/release-0.8.0.pert`:

1. `RELEASE_080_GATE_DESIGN` fixes version, public compatibility, and
   exclusion boundaries.
2. `RELEASE_080_INPUT_READINESS` verifies the three accepted release inputs.
3. `RELEASE_080_PREPARATION` aligns version-bearing source and passes the
   complete local and installed-package gate.
4. `RELEASE_080_CANDIDATE` commits and accepts one immutable tarball after
   clean-source, external-availability, protected-route, and package checks.
5. `RELEASE_080_PUBLISH` pushes the exact release commit and annotated tag,
   waits for CI, creates the GitHub prerelease, and publishes the same tarball
   exactly once to npm `beta`.
6. `RELEASE_080_ACCEPTANCE` independently verifies durable public identity
   and installed behavior without moving npm `latest`.

The user's 2026-08-07 instruction to proceed through release authorizes the
local gate-design, input-readiness, source-preparation, and candidate-
acceptance tasks in dependency order. It cannot bind an artifact that did not
yet exist. Before PUBLISH, present the exact release commit, tree, retained
tarball identity, proposed tag, GitHub Release body and assets, npm operation,
target refs, and maximum write count at a new user boundary. Plan state is
sequencing evidence and does not replace that candidate-specific authority.

## 3. Gate design and accepted-input readiness

Gate design must bind Requirements 21.15, ADR 0003, this procedure, the basic
design, the release plan, and regression tests. Input readiness must require:

- the complete retained pre-advance `ADAPTER-001` plan and final integration
  acceptance;
- the complete retained pre-advance `HIST-DAG-001` plan and final historical
  DAG acceptance;
- the accepted `DECL-ID-001` correction and focused regression cases; and
- current source proof of the exact public counts, package exclusions,
  installed behavior, compatibility, and no-write boundaries.

Neither gate changes package identity or external state.

## 4. Source-preparation gate

Update and verify together:

- `package.json`, both root lockfile version entries, adapter peer versions,
  and `src/version.ts`;
- a dated `0.8.0` CHANGELOG section and comparison links;
- README current-channel, exact-pin, migration, compatibility, subpath, and
  rollback guidance;
- release records, tests, goldens, self-use registration, and shared agent
  policy; and
- dependency audits, complete Node.js 22 repository gate, adapter package
  gates, temporary link, isolated package, and beta-only publication
  normalization.

This gate performs no external write and creates no retained candidate.

## 5. Candidate gate

Before the first external write:

1. require clean committed source identifying `0.8.0` and `v0.8.0`;
2. repeat the complete repository and isolated-package gates under Node.js 22;
3. prove local and remote `v0.8.0`, the GitHub Release, and
   `perttool@0.8.0` are absent;
4. record `beta=latest=0.7.1` and confirm `alpha` remains absent;
5. verify protected Git, GitHub, and process-scoped npm routes without
   displaying credentials;
6. build one tarball outside the worktree and record its timestamp, file
   count, packed and unpacked sizes, SHA-1, SHA-256, and npm integrity; and
7. install and verify the retained bytes, including 45 commands, 21 schemas,
   122 root and Node exports, 45 Core exports, `dag history`, public subpaths,
   declaration identity, and private-adapter exclusion.

Candidate acceptance performs read-only external checks. Any source,
artifact, external-baseline, route, or authorization change invalidates the
candidate or requires explicit reassessment.

The accepted candidate identity and preflight are recorded in
[`0.8.0-candidate.md`](0.8.0-candidate.md). GitHub reports no branch
protection for `main`; the acceptance record therefore distinguishes that
fact from the successful authenticated `secdat` fast-forward dry-run and
makes no branch-protection claim.

## 6. Separately authorized PUBLISH

Only after the user authorizes the frozen candidate and write set:

1. push and verify the clean release commit on `origin/main` through the
   configured `secdat` route;
2. require successful Node.js 22 and 24 CI for that commit;
3. create and push annotated `v0.8.0`, then verify its peeled target;
4. create a GitHub prerelease with the retained tarball and `SHA256SUMS`;
5. download, compare, install, and exercise the GitHub asset in isolation;
6. publish that identical tarball exactly once to npm `beta` through
   `secdat`; and
7. verify `beta=0.8.0`, unchanged `latest=0.7.1`, and absent `alpha`.

Never blindly retry an ambiguous external mutation. Read back durable state
first and resume only a demonstrably missing idempotent step.

## 7. Durable acceptance and remaining boundaries

Acceptance requires matching local, remote, tag, CI, GitHub, npm, and tarball
identity; exact and beta isolated installations; all accepted public counts
and behavior; private-adapter exclusion; compatibility; and an exact `0.7.1`
rollback installation. Record immutable publication-time registry facts
separately from any later dist-tag change.

npm `latest` promotion, public VSIX release, both input-plan advances,
release-plan advance, Issue mutation, `SCM-001`, and unrelated work remain
separate decisions.

## 8. Restart rules

- A source change after candidate acceptance invalidates the candidate and
  returns to the candidate gate.
- A registry, tag, Release, route, or CI-baseline change requires readback and
  reassessment before any write.
- An ambiguous non-idempotent response is never retried blindly.
- A changed candidate or write set requires a new explicit PUBLISH
  authorization.
