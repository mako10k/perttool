## 1. Decision and scope

Select suffix-free `0.9.0` for the first public Grammar 7 and CLI Contract 8
boundary after `0.8.1`. The release publishes milestone criterion sets,
caller-asserted receipts, committed migration provenance, acceptance-aware
check, analysis, Next and canonical advance, historical milestone acceptance,
and the accepted read-only adapter projections.

The exact public source boundary is 53 commands, 23 root schemas, 129 key- and
reference-identical root and Node runtime exports, and 45 portable Core runtime
exports. `0.8.2` would understate the breaking grammar, command, result,
schema, authority, migration, and advance changes.

The public npm artifact retains `perttool`, `perttool/core`, `perttool/node`,
and the schema subpath. Private LSP, VSIX, and MCP workspaces remain excluded.
This release does not publish a VSIX, create public adapter package identities,
move npm `latest`, advance a plan, or mutate an Issue.

## 2. Work packages and authority

The dependency order is fixed by `plans/release-0.9.0.pert`:

1. `RELEASE_090_GATE_DESIGN` fixes version, compatibility, migration, and
   exclusion boundaries.
2. `RELEASE_090_INPUT_READINESS` verifies every accepted release input.
3. `RELEASE_090_PREPARATION` aligns version-bearing source and passes the
   complete local and installed-package gate.
4. `RELEASE_090_CANDIDATE` accepts one immutable tarball after clean-source,
   availability, route, and package verification.
5. `RELEASE_090_PUBLISH` pushes the exact release commit and annotated tag,
   waits for CI, creates the GitHub prerelease, and publishes the same tarball
   exactly once to npm `beta`.
6. `RELEASE_090_ACCEPTANCE` independently verifies durable public identity and
   behavior without moving npm `latest`.

The user's 2026-08-13 instructions authorized the documentation commit,
`v0.8.1` baseline integration, local release-plan creation, gate design, input
readiness, source preparation, candidate acceptance, and then the exact
PUBLISH batch. That batch is complete. It does not authorize durable release
acceptance, npm `latest`, public VSIX publication, plan advance, Issue
mutation, or unrelated external work.

## 3. Gate design and accepted inputs

Gate design binds Requirements 21.16, ADR 0003, this procedure, the basic
design, the release plan, migration guidance, and focused release tests. Input
readiness requires:

- the canonically advanced complete `MILESTONE-ACCEPT-001` plan and final
  cross-surface acceptance;
- the accepted historical milestone-acceptance reconstruction;
- the current Help and documentation reconciliation;
- the Point-default and private VSIX duration-presentation slices;
- the published Issue #9 correction and the accepted Issue #11 correction; and
- direct verification of Grammar 7, Contract 8, exact public counts,
  compatibility, package exclusions, and no-write boundaries.

Neither gate changes package identity or external state.

## 4. Source-preparation gate

Update and verify together:

- `package.json`, both root lockfile version entries, adapter peer versions,
  `src/version.ts`, and the private MCP server version;
- a dated `0.9.0` CHANGELOG section and comparison links;
- README current-channel, exact-pin, migration, compatibility, and rollback
  guidance;
- release records, tests, goldens, self-use registration, and shared agent
  policy; and
- dependency audits, complete Node.js 22 repository gate, adapter package
  gates, temporary link, isolated package, and beta-only publication
  normalization.

This gate performs no external write and creates no retained candidate.

## 5. Candidate and publication boundaries

Candidate acceptance begins only from clean committed `0.9.0` source. It must
repeat the complete gate, prove local and remote `v0.9.0`, the GitHub Release,
and `perttool@0.9.0` unused, read back the public channel baseline, verify
authenticated routes without exposing credentials, and retain one immutable
tarball outside the worktree with complete identity and installed-package
evidence.

Publication requires a later exact-candidate authorization. Push, annotated
tag, GitHub prerelease, npm publish, and every readback are bounded separate
writes. npm publication moves only `beta`; a future `latest` promotion remains
a separately authorized post-acceptance operation. Ambiguous external writes
are never blindly retried.

## 6. Publication stopping point

PUBLISH is complete from release commit `3aca4f0`, annotated tag `v0.9.0`, CI
run `31670558276`, GitHub prerelease `369687054`, and one npm `beta`
publication of the retained SHA-256 `88e51bfe...37345e7` tarball. npm reports
`beta=0.9.0`, unchanged `latest=0.8.1`, and no `alpha`. Only
`RELEASE_090_ACCEPTANCE` is ready, recommended, and startable. Durable
acceptance, `latest`, VSIX publication, plan advance, and Issue mutation remain
separate.
