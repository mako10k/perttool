## 1. Observed failure

Manual run `34113325516` attempt 1 passed Node.js 22. Its Node.js 24 job passed
1,341 tests, English and documentation checks, 46-plan self-use, and isolated
LSP and MCP gates. After downloading VS Code 1.101.0, the first
`code --list-extensions --show-versions` read exceeded the harness's
120-second timeout under Xvfb. Attempt 2 reran the failed Node.js 24 job and
passed against the unchanged release commit. Main push run `34115992442` then
passed Node.js 22 and 24 against the same commit.

Accepted `0.9.2`, `0.10.0`, and `0.10.5` release records show the same
extension-inventory timeout followed by a successful bounded failed-job rerun.
The recurrence is therefore a repository test-harness condition, not evidence
of a Planning Pool source or immutable-candidate difference.

## 2. Causal classification

- Root cause of the recurring CI failure: the supported-host harness coupled
  an independent extension-registry assertion to the lifecycle of a second
  complete VS Code CLI process. The requested fact was already present in the
  `extensions.json` file written by the preceding install or uninstall, but
  the harness required `code --list-extensions --show-versions` to initialize
  its complete CLI service graph, scan that file, and terminate before it
  accepted the same fact.
- Upstream internal boundary: the available attempt-1 evidence cannot identify
  which await or active handle inside VS Code 1.101.0 prevented that one
  process from terminating. The old timeout path discarded stdout and stderr,
  did not retain VS Code logs or a process snapshot, and the unchanged command
  later passed. This missing historical discriminator does not remain in the
  repository acceptance path after the direct registry correction.
- Contributing causes: the old generic runner signaled only its direct child,
  rejected before process closure, and omitted captured output from the error.
- Escape cause: prior releases used whole-job reruns without removing the
  unnecessary process-lifecycle dependency. Correction 1.0 narrowed that rerun
  to one command, but its retry retained the same causal dependency instead of
  removing it.

## 3. Corrective and recurrence-prevention changes

Exact VS Code 1.101.0 source inspection confirms that
[`CliMain.run` and `initServices`](https://github.com/microsoft/vscode/blob/dfaf44141ea9deb3b4096f7cd6d24e00c147a4b1/src/vs/code/node/cliProcessMain.ts#L88-L222)
first construct state, configuration, profile, request, scanner, and extension-
management services before `ExtensionManagementCLI.listExtensions` runs. The
[profile scan](https://github.com/microsoft/vscode/blob/dfaf44141ea9deb3b4096f7cd6d24e00c147a4b1/src/vs/platform/extensionManagement/common/extensionsScannerService.ts#L607-L630)
ultimately obtains the requested user-extension inventory from the profile
registry. A local 50-iteration replay of the exact failed install/list sequence
completed every list in less than 0.5 seconds, so the historical internal wait
could not be reconstructed from a successful replay.

`scripts/check-vsix-host.mjs` now:

- reports a typed timeout with the command, timeout, stdout, and stderr;
- terminates the POSIX subprocess group and waits for close before returning
  the timeout;
- retains the necessary VS Code CLI install and uninstall operations;
- independently parses the CLI-owned `extensions.json` after each operation;
- verifies the exact extension ID, version, relative location, VSIX source,
  and absolute installed location after install; and
- requires the same registry to be exactly empty after uninstall.

There is no extension-inventory retry and no second VS Code list process.
Executable regression tests prove captured timeout diagnostics, descendant
closure, direct file-backed registry parsing, and fail-closed rejection of a
non-array registry. Release regression checks require the exact attempt-1
failure, attempt-2 recovery, unchanged candidate identity, current plan index,
and current agent guidance.
