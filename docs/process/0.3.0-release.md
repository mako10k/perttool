## 1. Decision and scope

Select suffix-free `0.3.0` for the first package that publishes accepted
Grammar 3, temporal deadline results, exact unit migration, NextResult v4
normal authority, and CLI Contract 4. The public grammar, command, schema, and
authority changes make `0.2.1` an inaccurate compatibility signal. `1.0.0`
remains reserved for a future stable-series decision.

The scheduling-and-units macro and its milestone-detail plans remain the
implementation authority. This release plan does not copy their task state.
`RELEASE_030_CONTRACT_4_READINESS` verifies the reached macro finish before
release-source preparation begins.

This release includes:

- Grammar 3 temporal and exact Decimal-or-fraction Duration source;
- temporal precedence and heuristic resource schedules with deadline state;
- `Perttool.AnalysisResult.v3` and `Perttool.NextResult.v4`;
- exact `Perttool.UnitMigrationResult.v2` and `project migrate-unit`;
- CLI Contract 4 dispatch, help, Guide, diagnostics, examples, and installed
  file-first workflows;
- other accepted changes recorded under `CHANGELOG.md`'s Unreleased section
  when the release source is prepared.

This gate does not:

- publish a partial SU-M3, SU-M4, or SU-M5 surface;
- promote `0.3.0` to npm `latest`;
- declare stable product maturity or select `1.0.0`;
- add Issue #3, LSP, VSIX, MCP, runtime i18n, human-override apply, durable
  audit, or Git integration;
- absorb the independent English-baseline workstream.

## 2. Work packages and authority

The dependency order is fixed by `plans/release-0.3.0.pert`.

1. `RELEASE_030_GATE_DESIGN` selects the version and fixes requirements, ADR,
   design, this procedure, plan, restart rules, and external authority.
2. `RELEASE_030_CONTRACT_4_READINESS` verifies the accepted scheduling-and-
   units finish and complete public Contract 4 boundary.
3. `RELEASE_030_PREPARATION` updates version-bearing source and release
   documentation and runs all local gates.
4. `RELEASE_030_CANDIDATE` accepts one clean local release commit after
   complete verification and read-only external availability checks.
5. `RELEASE_030_PUBLISH` performs the authorized Git push, annotated tag,
   GitHub prerelease, and npm `beta` publication from one tarball.
6. `RELEASE_030_ACCEPTANCE` records durable identity and public-channel
   verification after publication.

The user's 2026-07-25 request to proceed through PUBLISH explicitly authorizes
the named `0.3.0` Git push, annotated `v0.3.0` tag, GitHub prerelease, and npm
`beta` publication only after all preceding gates pass. It does not authorize
npm `latest` promotion or completion of the later acceptance task.

## 3. Contract 4 readiness gate

Before release preparation:

1. `plans/scheduling-units.pert` must have reached and advanced
   `SCHEDULING_UNITS_ACCEPTED`.
2. SU-M3 acceptance must cover calendar projection, release-aware temporal
   precedence and heuristic resource schedules, deadline evaluation,
   AnalysisResult v3, and NextResult v4 target Core.
3. SU-M5 acceptance must atomically activate Grammar 3, CLI Contract 4,
   result schemas, root exports, descriptor dispatch/help, Guide, README,
   installed workflows, and NextResult v4 normal authority.
4. A complete known NextResult v4 must remain the only normal start
   authority; unknown or incomplete results must fail closed.
5. Unit migration must preserve exact values, use source-preserving atomic
   candidates and safe writes, reject invented members, and satisfy no-op,
   repetition, and qualified inverse behavior.
6. No open acceptance finding may be hidden in release documentation.

## 4. Source-preparation gate

Update the following in one coherent release-source change:

- `package.json` and both root package entries in `package-lock.json`;
- the hard-coded CLI/tool version in `src/version.ts`;
- `CHANGELOG.md`, including a dated `0.3.0` section and comparison link;
- README installation, Contract 4, temporal, and migration examples;
- release tests, goldens, and package checks;
- current release guidance and plan metadata.

The prepared source must continue to use `publishConfig.tag=beta`. It must not
encode `latest` promotion into package publication.

Run under Node.js 22:

```sh
npm ci
npm run check
git diff --check
```

Review the intended diff by file and hunk before creating the release commit.

## 5. Candidate gate

Before the first external write:

1. Confirm package, lockfile, `perttool --version`, and intended tag agree on
   `0.3.0` / `v0.3.0`.
2. Confirm the complete repository and isolated-package Contract 4 gates pass.
3. Confirm publish normalization with an authentication-free dry run.
4. Establish that `perttool@0.3.0` is unpublished.
5. Establish that local and remote `v0.3.0` tags and a GitHub release with that
   tag do not exist.
6. Record npm `beta`, `latest`, and `alpha`; the expected baseline is
   `beta=latest=0.2.0` and `alpha=0.1.0-alpha.2`.
7. Verify the required `secdat exec git`, `secdat exec gh`, and process-scoped
   `NPM_TOKEN` routes without displaying credentials.
8. Commit the complete candidate and require a clean worktree.

A changed external baseline or unavailable credential route stops PUBLISH for
review. It does not authorize a different version, tag, or dist-tag operation.

## 6. Authorized PUBLISH

After the candidate gate:

1. Push the clean release commit to `origin/main` through `secdat exec git`.
2. Verify that `origin/main` resolves to the release commit.
3. Create annotated `v0.3.0` at that commit, push it through the required
   route, and verify its peeled remote target.
4. Generate one tarball outside the worktree and retain it for every
   remaining check and publication operation.
5. Run `scripts/check-package.sh` against that exact tarball.
6. Create a GitHub prerelease for `v0.3.0` and attach the tarball and
   `SHA256SUMS` through `secdat exec gh`.
7. Download, hash, install, and exercise that GitHub asset in isolation.
8. Inject `NPM_TOKEN` only into the publication process and publish the same
   tarball exactly once through `scripts/publish-npm.sh --publish`.
9. Verify `beta=0.3.0` and that `latest=0.2.0` is byte-for-byte unchanged from
   the pre-publication baseline.

Do not retry an ambiguous GitHub or npm mutation. Inspect the remote tag,
release assets, registry version, integrity, and dist-tags first, then resume
only the missing idempotent step.

## 7. PUBLISH completion evidence

`RELEASE_030_PUBLISH` is done only when the work record identifies:

- the release commit and peeled `v0.3.0` target;
- the GitHub prerelease URL and attached asset names;
- the common SHA-256 of the local and downloaded GitHub tarballs;
- the npm version, integrity, and registry tarball identity;
- npm `beta=0.3.0` and unchanged `latest=0.2.0`;
- successful isolated installation from the GitHub asset and npm registry;
- `perttool 0.3.0`, Contract 4 help and command discovery, temporal/deadline
  output, exact unit migration, complete NextResult v4, and file-first
  workflow results.

The later acceptance record may consolidate this evidence but cannot change
the immutable release artifact.

## 8. Restart and rollback

- Before any external write, correct source or tests and rerun the candidate
  gate.
- After pushing only the release commit, inspect `origin/main` and resume from
  tag creation; do not create a second release commit silently.
- Never rewrite a published annotated tag. If tagged source is wrong, stop and
  select a new version through a new release decision.
- After creating a GitHub release or publishing to npm, inspect durable state
  before retrying. npm versions and published release artifacts are immutable;
  fix forward with a new version rather than unpublish.
- If npm publication succeeds but immediate reads return propagation-time
  `E404`, use the bounded verification in `scripts/publish-npm.sh`; do not
  publish again.
- If `latest` changes unexpectedly, stop. Do not perform a compensating
  dist-tag mutation without separate explicit authorization.

Rollback for consumers means pinning `perttool@0.2.0` while a separately
reviewed Contract 4 fix is prepared. Runtime aliases are not restored.
