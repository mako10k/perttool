# `v0.10.0` Temporal Scheduling Beta Release Procedure

- Status: Gate design accepted 1.0
- Decision date: 2026-08-18
- Target version: `0.10.0`
- Product maturity: beta
- GitHub channel: prerelease
- npm publication tag: `beta`
- Versioning: [ADR 0003](../adr/0003-beta-versioning.md)
- Release plan: [`release-0.10.0.pert`](../../plans/release-0.10.0.pert)
- Accepted inputs: [`contract9-public-integration-acceptance.md`](contract9-public-integration-acceptance.md) and [`temporal-schedule-acceptance.md`](temporal-schedule-acceptance.md)

## 1. Decision and scope

Select suffix-free `0.10.0` for the first public Grammar 8 and CLI Contract 9
package after `0.9.4`. The release publishes calendar and availability
maintenance, event constraints, forward and required schedules, POSTDUE
projection, source-preserving temporal mutation, Grammar 7 to 8 migration,
and replacement Contract 9 results and schemas as one boundary.

The exact public surface is 56 commands, 23 active root schemas, 129 root and
Node runtime exports, and 45 Core exports. `Perttool.AdvanceResult.v3` remains
unchanged. Private LSP, VSIX, and MCP workspaces remain excluded from the npm
tarball.

## 2. Dependency order

1. `RELEASE_0100_GATE_DESIGN` fixes this procedure and its normative trace.
2. `RELEASE_0100_INPUT_READINESS` verifies the accepted temporal inputs.
3. `RELEASE_0100_PREPARATION` aligns version-bearing source and complete
   local and installed-package gates.
4. `RELEASE_0100_CANDIDATE` commits clean source and freezes one immutable
   tarball after availability and authenticated-route preflight.
5. `RELEASE_0100_PUBLISH` consumes only that exact candidate under a separate
   user authorization and performs bounded Git, GitHub, CI, and npm writes.
6. `RELEASE_0100_ACCEPTANCE` independently verifies durable identity,
   behavior, compatibility, and rollback.

## 3. Source-preparation gate

Preparation aligns `package.json`, both root lockfile entries, CLI and adapter
versions, MCP identity, CHANGELOG, README, migration guidance, tests, goldens,
self-use, and release records. It requires the complete Node.js 22 repository,
private-adapter, supported-host VSIX, temporary-link, and isolated-package
gates. It performs no remote or registry write and retains no candidate.

## 4. Candidate and publication boundaries

Candidate acceptance starts only from clean committed `0.10.0` source. It
proves local and remote tag, GitHub Release, and npm-version availability,
reads current distribution tags, checks authenticated routes without exposing
credentials, and retains one immutable tarball outside the worktree with its
complete identity and installed behavior.

PUBLISH requires a later authorization naming that exact candidate and
external batch. It pushes and verifies the release commit and annotated tag,
requires Node.js 22 and 24 CI, creates one GitHub prerelease and SHA256SUMS,
and publishes the identical tarball exactly once to npm `beta` through
`secdat`. Ambiguous writes are read back and never blindly retried.

## 5. Stopping points

Publication leaves npm `latest` unchanged. Durable acceptance, any later
`latest` promotion, public VSIX publication, plan advance, and Issue mutation
are separate decisions. Gate design and input readiness do not change package
identity, commit source, or perform an external write.
