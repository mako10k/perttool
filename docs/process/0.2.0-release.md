# `v0.2.0` Contract 3 Beta Release Procedure

- Status: Candidate accepted; distribution authorized
- Decision date: 2026-07-24
- Target version: `0.2.0`
- Product maturity: beta
- GitHub channel: prerelease
- npm publication tag: `beta`
- Current default npm version: `latest=0.1.0`
- Versioning: [ADR 0003](../adr/0003-beta-versioning.md)
- Contract: [CLI Contract 3](../specs/cli-contract-3.md)
- Plan: [`release-0.2.0.pert`](../../plans/release-0.2.0.pert)

## 1. Decision and scope

Select suffix-free `0.2.0` for the first package that publishes CLI Contract
3. The published `0.1.0` package remains Contract 2. Contract 3 intentionally
renames commands, rejects the replaced Contract 2 spellings, and changes the
CLI JSON envelope, so `0.1.1` would understate the compatibility change.
`1.0.0` remains reserved for a future stable-series decision.

The release includes the complete accepted Contract 3 source and its isolated
installed-package file-first acceptance. It also includes the other changes
already recorded under `CHANGELOG.md`'s Unreleased section when the release
source is prepared.

This gate does not:

- change `package.json`, the lockfile, the CLI version, or CHANGELOG by itself;
- authorize a Git push, tag, GitHub Release, npm publication, or dist-tag
  mutation;
- promote `0.2.0` to npm `latest`;
- declare stable product maturity or select `1.0.0`;
- add Issue #3, LSP, VSIX, MCP, runtime i18n, or human-override apply/audit;
- absorb the independent English-baseline workstream.

Remaining English-baseline repository migration stays independently governed
by `plans/english-baseline.pert`. Package, runtime, help, README, and CHANGELOG
acceptance for `0.2.0` remain part of this release gate.

## 2. Work packages

The dependency order is fixed by `plans/release-0.2.0.pert`.

1. `RELEASE_020_GATE_DESIGN` selects the version and fixes this procedure,
   requirements, specification, plan, restart rules, and external authority
   boundary.
2. `RELEASE_020_PREPARATION` updates version-bearing source and release
   documentation together. It performs no remote or registry write.
3. `RELEASE_020_CANDIDATE` accepts one clean local release commit after the
   complete repository and package gates and read-only version-availability
   checks. It performs no remote or registry write.
4. `RELEASE_020_DISTRIBUTION` is blocked until the user explicitly authorizes
   the named `0.2.0` Git push, annotated tag, GitHub prerelease, and npm
   `beta` publication batch.
5. `RELEASE_020_ACCEPTANCE` verifies durable identity and installation
   evidence and records the accepted release.

The release plan finishes at durable `0.2.0` beta acceptance. Any later
`latest` promotion is a separate post-acceptance decision and mutation.

Update the following in one coherent release-source change:

- `CHANGELOG.md`, including a dated `0.2.0` section and comparison link;

encode `latest` promotion into package publication.

Run:

```sh

git diff --check
```

Review the intended release diff by file and hunk before creating the release
commit. The candidate task must record a clean worktree and the exact commit
that passed the gate.

## 4. Candidate gate

Completed on 2026-07-25. Local package, lockfile, CLI, and intended tag
identities agree on `0.2.0` / `v0.2.0`; the complete repository and package
gate passed; `perttool@0.2.0`, local and remote `v0.2.0`, and the GitHub
release were unused; and npm reported `beta=0.1.0`, `latest=0.1.0`, and
`alpha=0.1.0-alpha.2`. The user then authorized the named Git force-update,
annotated tag, GitHub prerelease, and npm `beta` publication batch. This
authorization does not include npm `latest`.

Before requesting external-write authorization:

1. Confirm `package.json`, lockfile root identity, `perttool --version`, and
   intended tag are all `0.2.0` / `v0.2.0`.
2. Confirm all repository checks, the isolated package installation, and the
   complete file-first workflow pass.
3. Confirm publish normalization remains unchanged with
   `scripts/publish-npm.sh --dry-run`.
4. Read the registry and establish that `perttool@0.2.0` is unpublished.
5. Confirm that local and remote `v0.2.0` tags do not already exist.
6. Record the current npm `beta` and `latest` values. The expected pre-release
   baseline is `beta=0.1.0` and `latest=0.1.0`; treat a different value as a
   changed external baseline and stop for review.
7. Confirm the remote configuration and the repository-required `secdat`
   routes without exposing credentials.

This gate validates a releasable commit, not the final release tarball. The
one distribution tarball is generated only after the release commit and
annotated tag have been fixed and verified.

## 5. Authorized distribution

After explicit user authorization for the complete named batch:

1. Push the clean release commit to `origin/main` through `secdat exec git`.
2. Verify that `origin/main` resolves to the release commit.
3. Create annotated `v0.2.0` at that commit, push it through the required
   route, and verify its peeled remote target.
4. Generate one tarball outside the worktree and retain it for every remaining
   check and publication operation.
5. Run `scripts/check-package.sh` against that exact tarball.
6. Create a GitHub prerelease for `v0.2.0` and attach the tarball and
   `SHA256SUMS` through `secdat exec gh`.
7. Install the downloaded GitHub asset in isolation and verify Contract 3,
   guidance, recommendation, and the file-first workflow.
8. Inject `NPM_TOKEN` only into the publication process and publish the same
   tarball exactly once through `scripts/publish-npm.sh --publish`.
9. Verify `beta=0.2.0` and verify that `latest` is byte-for-byte unchanged
   from the pre-publication baseline.

Do not retry an ambiguous GitHub or npm mutation. Inspect the remote tag,
release assets, registry version, integrity, and dist-tags first, then resume
only the missing idempotent step.

## 6. Acceptance evidence

The release is accepted only when one durable record identifies:

- the release commit and peeled `v0.2.0` target;
- the GitHub prerelease URL and asset names;
- the common SHA-256 of the local, GitHub, and registry tarballs;
- npm integrity and registry metadata;
- npm `beta=0.2.0` and the unchanged `latest` value;
- successful isolated installation from both GitHub and npm;
- `perttool 0.2.0`, Contract 3 command rejection/acceptance, complete
  `NextResult.v3`, read-only `agent help`, and the file-first workflow;
- the exact verification commands and any propagation-time observations.

The acceptance record is a post-release repository change. It does not alter
the immutable release artifact.

## 7. Restart and rollback

- Before any external write, correct the source or tests and rerun the
  candidate gate.
- After pushing only the release commit, inspect `origin/main` and resume from
  tag creation; do not push another release commit silently.
- After publishing an annotated tag, never rewrite it. If the tagged source is
  wrong, stop and select a new version through a new release decision.
- After creating a GitHub release or publishing to npm, inspect durable state
  before retrying. npm versions and published release artifacts are immutable;
  fix forward with a new version rather than unpublish.
- If npm publication succeeds but immediate reads return propagation-time
  `E404`, use the bounded verification already implemented by
  `scripts/publish-npm.sh`; do not publish again.
- If `latest` changes unexpectedly, stop. Do not attempt a compensating
  dist-tag mutation without separate explicit authorization.

Rollback for consumers means pinning `perttool@0.1.0` while a separately
reviewed Contract 3 fix is prepared. Runtime aliases are not restored.
