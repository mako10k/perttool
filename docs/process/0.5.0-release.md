## 1. Decision and scope

Select suffix-free `0.5.0` for the first package that publishes accepted
Grammar 5, CLI Contract 6, exact lifecycle events, read-only project history,
and read-only velocity observation. The grammar, commands, options, JSON
envelopes, result schemas, and lifecycle semantics change together. `0.4.1`
would understate that compatibility boundary, while `1.0.0` remains reserved
for a future stable-series decision.

The completed project-actuals and English-baseline plans remain the
implementation and repository-language authorities. This release plan does
not restore or duplicate their completed task state.
`RELEASE_050_CONTRACT_6_READINESS` verifies both reached finishes and accepted
source/package boundaries before release-source preparation begins.

This release includes:

- Grammar 5 task-owned work events and suspended task state;
- governed `task start`, `task suspend`, `task resume`, and eventful
  `task finish`;
- `Perttool.ProjectHistoryResult.v1` and
  `Perttool.VelocityObservationResult.v1`;
- `Perttool.MutationResult.v3`, `Perttool.AnalysisResult.v4`,
  `Perttool.NextResult.v5`, and `Perttool.UnitMigrationResult.v3`;
- the 33-command CLI Contract 6 registry, help, Guide, diagnostics, schemas,
  package-root exports, and installed file-first workflow;
- retained Grammar 1/2/3/4 meanings, governance controls, and legacy
  status-only finish; and
- the accepted English repository baseline.

This gate does not:

- promote `0.5.0` to npm `latest` or close Issue #4;
- mutate Git through perttool or automatically adopt observed velocity;
- select semantics or implementation for REOPEN, ADV-001, override apply,
  durable audit, or MIG-08;
- add Issue synchronization, LSP, VSIX, MCP, or runtime i18n; or
- declare stable product maturity or select `1.0.0`.

## 2. Work packages and authority

The dependency order is fixed by `plans/release-0.5.0.pert`.

1. `RELEASE_050_GATE_DESIGN` fixes requirements, ADR, design, this procedure,
   the release plan, restart rules, and authority boundaries.
2. `RELEASE_050_CONTRACT_6_READINESS` verifies reached actuals and English
   acceptance, the active public source/package boundary, and the absence of
   hidden acceptance findings.
3. `RELEASE_050_PREPARATION` aligns version-bearing source, migration and
   release documentation, tests, goldens, and package validation.
4. `RELEASE_050_CANDIDATE` accepts one clean release commit and one immutable
   tarball after complete local and read-only external preflight.
5. `RELEASE_050_PUBLISH` pushes the release commit and annotated tag, creates
   the GitHub prerelease, and publishes the same tarball once to npm `beta`.
6. `RELEASE_050_ACCEPTANCE` records durable identity and public-channel
   verification without changing the immutable artifact.

The user's 2026-07-29 instruction authorizes this complete named `0.5.0`
sequence, including the external PUBLISH batch, once all predecessor gates
pass. The same instruction requests exact local installation of
`perttool@0.5.0` only after release acceptance. It does not authorize npm
`latest` promotion, Issue #4 closure, or any non-goal above. Plan state
records the boundary but is not a substitute for the user instruction.

The gate-design requirements, ADR, design, procedure, self-use registration,
tests, and exact completed plan snapshot passed the complete repository and
package gates. Git commit `1641a32` records that pre-advance snapshot.
Canonical governed advance removed only `RELEASE_050_GATE_DESIGN` and
`RELEASE_050_PLANNING_STARTED`, retained reached
`RELEASE_050_GATE_ACCEPTED`, and preserved the ready set containing only
`RELEASE_050_CONTRACT_6_READINESS`.

## 4. Source-preparation gate

Update the following in one coherent release-source change:

- `package.json` and both root package entries in `package-lock.json`;
- the hard-coded CLI/tool version in `src/version.ts`;
- `CHANGELOG.md`, including a dated `0.5.0` section and comparison link;
- README installation, current-channel, lifecycle, history, observation, and
  Contract 5-to-6 migration guidance;
- release tests, goldens, package checks, and installed file-first checks;
- current release guidance and plan metadata.

The migration guidance must state that:

- every JSON envelope changes to `cli_contract_version=6`;
- lifecycle, history, observation, mutation, analysis, next, and unit
  migration result identities change exactly as specified;
- Contract 6 adds five commands and eventful-finish options;
- Grammar 5 adds task-owned work events and suspended state;
- older runtimes fail closed on Grammar 5 and Contract 6 spellings; and
- no Contract 5 runtime switch or compatibility alias is provided.

The prepared source must continue to use `publishConfig.tag=beta`. It must not
encode `latest` promotion, Issue closure, or deferred capability claims into
the publication operation.

Run under Node.js 22:

```sh
npm ci
npm run check
git diff --check
```

Review the intended diff by file and hunk before creating the release-source
commit.

## 5. Candidate gate

Before the first external write:

1. Confirm package, lockfile, `perttool --version`, and intended tag agree on
   `0.5.0` and `v0.5.0`.
2. Confirm the complete repository and isolated-package Contract 6 gates pass.
3. Confirm publish normalization with an authentication-free dry run.
4. Establish that `perttool@0.5.0` is unpublished.
5. Establish that local and remote `v0.5.0` tags and a GitHub release with
   that tag do not exist.
6. Record npm `beta`, `latest`, and `alpha`; the expected baseline is
   `beta=latest=0.4.0` and `alpha=0.1.0-alpha.2`.
7. Verify the required `secdat exec git`, `secdat exec gh`, and
   process-scoped `NPM_TOKEN` routes without displaying credentials.
8. Commit the complete candidate and require a clean worktree.
9. Build one tarball from that candidate HEAD outside the worktree, run the
   complete package gate against those exact bytes, record its SHA-256, and
   retain it unchanged for GitHub and npm.
10. Reconfirm that the user's named `0.5.0` PUBLISH authorization still
    applies to the unchanged candidate and external baseline.

A changed external baseline, unavailable protected route, or changed artifact
stops PUBLISH for review. It does not authorize a different version, tag,
artifact, or dist-tag operation.

## 6. Authorized PUBLISH

Only after all preceding gates:

1. Push the clean release commit to `origin/main` through `secdat exec git`.
2. Verify that `origin/main` resolves to the release commit.
3. Create annotated `v0.5.0` at that commit, push it through the required
   route, and verify its peeled remote target.
4. Create a GitHub prerelease for `v0.5.0`, attach the retained tarball and
   `SHA256SUMS`, then verify the public asset identity.
5. Download, hash, install, and exercise that GitHub asset in isolation.
6. Inject `NPM_TOKEN` only into the publication process and publish the
   downloaded GitHub tarball exactly once through
   `scripts/publish-npm.sh --publish`.
7. Verify `beta=0.5.0` and that `latest=0.4.0` is unchanged.

Do not retry an ambiguous GitHub or npm mutation. Inspect the remote tag,
release assets, registry version, integrity, and dist-tags first, then resume
only a demonstrably missing idempotent step.

## 7. Completion evidence

`RELEASE_050_PUBLISH` is done only when a durable record identifies:

- the release commit and peeled `v0.5.0` target;
- the GitHub prerelease URL and attached asset names;
- the common SHA-256 of candidate, GitHub, and npm tarballs;
- npm version, integrity, registry identity, `beta=0.5.0`, and unchanged
  `latest=0.4.0`;
- successful isolated installation from GitHub and npm;
- `perttool 0.5.0`, Grammar 5, CLI Contract 6, lifecycle, suspended NextResult
  v5, project history, velocity observation, governance, unit migration,
  help/Guide, and file-first workflow results; and
- exact commands, bounded propagation observations, and whether any mutation
  returned an ambiguous result.

`RELEASE_050_ACCEPTANCE` must independently re-read both public channels,
verify the immutable identities and behaviors, record all 19p as accepted,
advance the plan to reached `RELEASE_050_ACCEPTED`, and leave npm `latest`
and Issue #4 unchanged.

After that acceptance, install exact `perttool@0.5.0` locally, verify the
resolved executable and Contract 6 identity, and record the result in the
release acceptance evidence. This exact install does not require or imply a
`latest` promotion.

## 8. Restart and rollback

- If stopped before any external write, rebuild and reverify from the current
  clean candidate commit; discard any changed candidate artifact.
- If the commit or tag push is ambiguous, read the remote reference before
  deciding whether a retry is necessary.
- If GitHub creation is ambiguous, read the release and asset inventory
  before any further mutation.
- If npm publication is ambiguous, read the exact version, registry tarball,
  integrity, and dist-tags before any retry.
- If a public artifact differs from the accepted candidate, stop acceptance;
  do not overwrite a tag, release asset, or published npm version.
- Consumers can roll back by pinning `perttool@0.4.0`. Do not repair a
  `0.5.0` problem by moving `latest` or republishing the same version.
