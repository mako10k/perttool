## 1. Decision and scope

Select suffix-free `0.7.1` for the backward-compatible Grammar 6 and CLI
Contract 7 patch that publishes the accepted `GUIDE-CONSISTENCY-001`
correction. The package changes runtime Guide text and related navigation,
command Help examples, diagnostic `help_topic` values, and the specification
and regression coverage of `PTCNV-210`. Current documentation also
distinguishes live registry state from prior publication-time facts.

This is not a documentation-only package change: Guide, Help, and diagnostic
navigation are distributed runtime values. A release is therefore required to
make the correction available to installed consumers. `0.7.1` expresses a
compatible correction; leaving the change unreleased would strand it in the
source checkout, while `0.8.0` would overstate the boundary.

The patch retains Grammar 6, CLI Contract 7, all 44 command paths and option
spellings, all 20 root schemas, every result identity and payload structure,
package-root exports, governance semantics, safe-write behavior, and
recommendation, temporal, and assurance authority. It adds no command, option,
schema, locale, network lookup, or automatic registry discovery.

## 2. Work packages and authority

The dependency order is fixed by `plans/release-0.7.1.pert`:

1. `RELEASE_071_SELF_REVIEW` fixes the compatibility judgment, requirements,
   ADR, design, procedure, plan, and tests.
2. `RELEASE_071_PREPARATION` changes version-bearing source and aligns the
   changelog, README, release records, goldens, audit, and package checks.
3. `RELEASE_071_CANDIDATE` accepts one clean release commit and one immutable
   tarball after complete local and read-only external preflight.
4. `RELEASE_071_PUBLISH` pushes the exact release commit and tag, waits for
   CI, creates the GitHub prerelease, and publishes the same tarball once to
   npm `beta`.
5. `RELEASE_071_ACCEPTANCE` independently records durable public identity and
   installed behavior without changing the artifact.

The user's initial 2026-08-05 confirmation authorized the exact plan candidate
and local `RELEASE_071_SELF_REVIEW`. The later instruction to proceed with the
release authorizes local `RELEASE_071_PREPARATION` and candidate acceptance.
The exact candidate commit and tarball were later presented at a user boundary
and separately authorized for `RELEASE_071_PUBLISH`. After publication, the
user separately selected and authorized the exact `perttool@0.7.1` npm
`latest` promotion. Neither instruction authorizes plan advance or Issue
mutation. Plan state is sequencing evidence and does not replace an explicit
external-write instruction.

## 3. Compatibility self-review gate

Self-review must verify all of the following before source preparation:

- the complete `GUIDE-CONSISTENCY-001` acceptance and seven HGC cases remain
  the implementation authority;
- Grammar 6 and CLI Contract 7 remain active and unchanged;
- command paths, options, effects, exits, result and schema identities,
  payload structure, package-root exports, and authority policies are
  unchanged;
- Guide value corrections, Help examples, diagnostic links, `PTCNV-210`, and
  current-versus-historical documentation labels are the complete release
  scope;
- package, lockfile, and CLI remain `0.7.0` during this gate;
- npm reports `beta=latest=0.7.0`, no maintained `alpha`, and no published
  `perttool@0.7.1`; and
- no remote or registry mutation occurs.

Accepted evidence is recorded in [`0.7.1-self-review.md`](0.7.1-self-review.md).

## 4. Source-preparation gate

Only after separate authorization for `RELEASE_071_PREPARATION`, update and
verify together:

- `package.json`, both root lockfile version entries, and `src/version.ts`;
- a dated `0.7.1` CHANGELOG section and comparison link;
- README current-channel, exact-pin, compatibility, and release guidance;
- release procedure, self-use registration, shared agent policy, tests, and
  goldens; and
- dependency audit, complete Node.js 22 repository gate, temporary link,
  isolated package, and beta-only publication normalization.

This gate performs no remote write and does not create the release candidate.

## 5. Candidate gate

Before the first external write:

1. require clean committed source with package, lockfile, CLI version, and
   intended tag equal to `0.7.1` and `v0.7.1`;
2. pass the complete repository and isolated-package gates under Node.js 22;
3. reconfirm that local and remote `v0.7.1`, the GitHub Release, and
   `perttool@0.7.1` are absent;
4. record `beta=latest=0.7.0` and confirm `alpha` remains absent;
5. verify protected Git, GitHub, and process-scoped npm routes without
   displaying credentials;
6. build one tarball outside the worktree and record its timestamp, file
   count, packed and unpacked sizes, SHA-1, SHA-256, and npm integrity; and
7. stop if source, artifact, authorization, or external baseline changes.

Candidate acceptance performs read-only external checks but no external
mutation. The retained tarball is immutable after acceptance.

`RELEASE_071_CANDIDATE` is accepted from source commit `a05b769` and the
retained 601-file, 660003-byte tarball with SHA-256
`5bf4723131b79f04b501ae02b7585c800ac8dc37f0f3a816eff837d670e4454c`.
Its exact identity, clean gate, route preflight, and installed-package evidence
are recorded in [`0.7.1-candidate.md`](0.7.1-candidate.md). No external state
changed; PUBLISH remains a separate user-authorized batch.

## 6. Separately authorized PUBLISH

Only after candidate acceptance and the user separately authorizes the exact
candidate and external batch:

1. push and verify the clean release commit on `origin/main` through
   `secdat exec git`;
2. require successful Node.js 22 and 24 CI for that commit;
3. create and push annotated `v0.7.1`, then verify its peeled target;
4. create a GitHub prerelease with the retained tarball and `SHA256SUMS`;
5. download, compare, install, and exercise the GitHub asset in isolation;
6. publish that identical tarball exactly once to npm `beta` through
   `secdat`; and
7. verify `beta=0.7.1`, unchanged `latest=0.7.0`, and absent `alpha`.

The authorized PUBLISH completed from release commit `eee0f05`, successful
Node.js 22 and 24 CI run `30969627120`, peeled annotated tag `v0.7.1`, GitHub
prerelease `365255925`, and one npm publication to `beta`. The candidate,
GitHub, and npm tarballs are byte-identical at SHA-256
`5bf4723131b79f04b501ae02b7585c800ac8dc37f0f3a816eff837d670e4454c`.
At publication, npm reported `beta=0.7.1`, unchanged `latest=0.7.0`, and no
`alpha`. Exact evidence is recorded in [`0.7.1-publish.md`](0.7.1-publish.md).

The user then separately authorized one exact post-publication dist-tag
mutation. Fresh registry readback and an unqualified isolated installation
confirmed `beta=latest=0.7.1`, no `alpha`, 44 commands, and 20 schemas. This
later fact is recorded in
[`0.7.1-latest-promotion.md`](0.7.1-latest-promotion.md) without changing the
publication-time boundary.

Do not retry an ambiguous external mutation. Read back durable state first and
resume only a demonstrably missing idempotent step.

## 7. Durable acceptance and remaining boundaries

Acceptance requires matching local, remote, tag, CI, GitHub, npm, and tarball
identity; exact and beta isolated installations; corrected Guide, Help,
diagnostic navigation and `PTCNV-210` behavior; unchanged Contract 7 identity
and authority; and an exact `0.7.0` rollback installation.

The publish operation itself did not move npm `latest`; the later separately
authorized promotion changed only that dist-tag. Durable acceptance is
complete in [`0.7.1-release-acceptance.md`](0.7.1-release-acceptance.md).
Release-plan and correction-plan advance, Issue mutation, and unrelated
backlog work remain separate.

## 8. Restart rules

- A source change after candidate acceptance invalidates the candidate and
  returns to the candidate gate.
- A registry, tag, Release, route, or CI-baseline change requires readback and
  reassessment before any write.
- An ambiguous non-idempotent response is never retried blindly.
- A changed candidate requires a new explicit PUBLISH authorization.
