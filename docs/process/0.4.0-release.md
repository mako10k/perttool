## 1. Decision and scope

Select suffix-free `0.4.0` for the first package that publishes accepted
Grammar 4, owner-aware goal and DAG mutation governance, and CLI Contract 5.
The grammar, command options, JSON envelopes, result schemas, and persistent
write authority change together. `0.3.1` would understate that compatibility
boundary, while `1.0.0` remains reserved for a future stable-series decision.

The completed governance plan and its acceptance record remain the
implementation authority. This release plan does not restore or duplicate
their completed task state. `RELEASE_040_CONTRACT_5_READINESS` verifies the
reached governance finish and accepted source/package boundary before
release-source preparation begins.

This release includes:

- Grammar 4 declared and effective owner/delegate metadata;
- owner-aware direct, batch, and advance planning and persistence;
- `Perttool.ProjectResult.v3`, `Perttool.MutationResult.v2`, and
  `Perttool.GovernanceDecision.v1`;
- CLI Contract 5 dispatch, options, help, Guide, diagnostics, warnings, and
  installed file-first workflows;
- retained Grammar 1/2/3 compatibility through effective default ownership;
- the Contract 4 temporal, deadline, exact unit-migration, and NextResult v4
  behavior already published in `0.3.0`; and
- other accepted changes recorded under `CHANGELOG.md`'s Unreleased section
  when release source is prepared.

This gate does not:

- publish a partial governance surface or a second `0.3.0` artifact;
- promote `0.4.0` to npm `latest`;
- close Issue #4;
- declare stable product maturity or select `1.0.0`;
- add authentication, verified identity, signatures, durable approval audit,
  technical prevention of direct editing, recommendation override apply,
  MIG-08, Git integration, Issue #3, LSP, VSIX, MCP, or runtime i18n; or
- absorb the independent English-baseline workstream.

## 2. Work packages and authority

The dependency order is fixed by `plans/release-0.4.0.pert`.

1. `RELEASE_040_GATE_DESIGN` selects the version and fixes requirements, ADR,
   design, this procedure, the release plan, restart rules, and external
   authority boundaries.
2. `RELEASE_040_CONTRACT_5_READINESS` verifies the reached governance finish,
   its accepted public source/package boundary, and the absence of hidden
   acceptance findings.
3. `RELEASE_040_PREPARATION` updates version-bearing source, migration and
   release documentation, tests, and package validation, then runs all local
   gates.
4. `RELEASE_040_CANDIDATE` accepts one clean local release commit and one
   immutable tarball after complete verification and read-only external
   availability checks.
5. `RELEASE_040_PUBLISH` performs an explicitly authorized Git push,
   annotated tag, GitHub prerelease, and npm `beta` publication from that
   tarball.
6. `RELEASE_040_ACCEPTANCE` records durable identity and public-channel
   verification after publication.

The user's 2026-07-27 requests authorized `RELEASE_040_GATE_DESIGN` and
`RELEASE_040_CONTRACT_5_READINESS`; the 2026-07-28 instruction to perform the
next release task authorizes `RELEASE_040_PREPARATION`. These instructions do
not authorize a Git push, tag, GitHub Release, npm publication, npm dist-tag
operation, or Issue mutation.
`RELEASE_040_PUBLISH` remains blocked until a separate user instruction
explicitly authorizes the named `0.4.0` external publication batch. Plan state
records the boundary but is planning evidence, not a substitute for that
instruction. npm `latest` promotion and Issue #4 closure remain separate
post-acceptance decisions.

## 5. Candidate gate

Before the first external write:

1. Confirm package, lockfile, `perttool --version`, and intended tag agree on
   `0.4.0` / `v0.4.0`.
2. Confirm the complete repository and isolated-package Contract 5 gates pass.
3. Confirm publish normalization with an authentication-free dry run.
4. Establish that `perttool@0.4.0` is unpublished.
5. Establish that local and remote `v0.4.0` tags and a GitHub release with
   that tag do not exist.
6. Record npm `beta`, `latest`, and `alpha`; the expected baseline is
   `beta=latest=0.3.0` and `alpha=0.1.0-alpha.2`.
7. Verify the required `secdat exec git`, `secdat exec gh`, and
   process-scoped `NPM_TOKEN` routes without displaying credentials.
8. Commit the complete candidate and require a clean worktree.
9. Build one tarball from that candidate HEAD outside the worktree, run the
   complete package gate against those exact bytes, record its SHA-256, and
   retain it unchanged for GitHub and npm.
10. Confirm that the named `0.4.0` PUBLISH authorization has been explicitly
    provided; otherwise retain the blocked plan state and stop before any
    external mutation.

A changed external baseline, unavailable credential route, or missing
authorization stops PUBLISH for review. It does not authorize a different
version, tag, artifact, or dist-tag operation.

## 6. Authorized PUBLISH

Only after all preceding gates and the separate named authorization:

1. Push the clean release commit to `origin/main` through `secdat exec git`.
2. Verify that `origin/main` resolves to the release commit.
3. Create annotated `v0.4.0` at that commit, push it through the required
   route, and verify its peeled remote target.
4. Create a GitHub prerelease for `v0.4.0`, attach the retained tarball and
   `SHA256SUMS`, then verify the public asset identity.
5. Download, hash, install, and exercise that GitHub asset in isolation.
6. Inject `NPM_TOKEN` only into the publication process and publish the same
   tarball exactly once through `scripts/publish-npm.sh --publish`.
7. Verify `beta=0.4.0` and that `latest=0.3.0` is byte-for-byte unchanged
   from the pre-publication baseline.

Do not retry an ambiguous GitHub or npm mutation. Inspect the remote tag,
release assets, registry version, integrity, and dist-tags first, then resume
only a demonstrably missing idempotent step.

## 7. PUBLISH completion evidence

`RELEASE_040_PUBLISH` is done only when the work record identifies:

- the release commit and peeled `v0.4.0` target;
- the GitHub prerelease URL and attached asset names;
- the common SHA-256 of the candidate and downloaded GitHub tarballs;
- the npm version, integrity, and registry tarball identity;
- npm `beta=0.4.0` and unchanged `latest=0.3.0`;
- successful isolated installation from the GitHub asset and npm registry;
- `perttool 0.4.0`, Grammar 4, Contract 5 help and command discovery,
  effective defaults, preview denial, authorized persistence, stale-digest
  rejection, batch decisions, unit-migration preservation, complete
  NextResult v4, and the file-first workflow results.

The later acceptance record may consolidate this evidence but cannot change
the immutable release artifact.

## 8. Restart and rollback

- Before any external write, correct source or tests and rerun the candidate
  gate.
- If authorization is absent, retain `RELEASE_040_PUBLISH` as blocked; do not
  infer authority from the plan, an earlier unrelated PUBLISH, or local
  acceptance.
- After pushing only the release commit, inspect `origin/main` and resume from
  tag creation; do not create a second release commit silently.
- Never rewrite a published annotated tag. If tagged source is wrong, stop
  and select a new version through a new release decision.
- After creating a GitHub release or publishing to npm, inspect durable state
  before retrying. npm versions and published release artifacts are
  immutable; fix forward with a new version rather than unpublish.
- If npm publication succeeds but immediate reads return propagation-time
  `E404`, use the bounded verification in `scripts/publish-npm.sh`; do not
  publish again.
- If `latest` changes unexpectedly, stop. Do not perform a compensating
  dist-tag mutation without separate explicit authorization.

Rollback for consumers means pinning `perttool@0.3.0` while a separately
reviewed Contract 5 fix is prepared. Runtime aliases are not restored.
